THE DATA

Thursday 10 April 2014, three days after the advisory. You look after Byte Bakery's servers (fictional, like every name and address here). The advisory says: “Only 1.0.1 and 1.0.2-beta releases of OpenSSL are affected including 1.0.1f and 1.0.2-beta1. Affected users should upgrade to OpenSSL 1.0.1g.”

  • servers.csv: the bakery's 7 servers and their OpenSSL versions (questions 1 and 3).
  • staging_trace.csv: the last 8 heartbeats the staging server received before the advisory. Normal logs show nothing; a developer had left debug tracing on, so each heartbeat's record_length (what arrived) and payload_length (what the sender claimed) were written down (question 2).

A heartbeat record is 1 byte type + 2 bytes length + the payload + at least 16 bytes of padding. No tools needed: the tables and arithmetic.

2. The check, line by line

Linerecord_lengthpayload_length1.0.1gThe arithmetic
1245echo5 + 19 = 24 ≤ 24: it fits, so 1.0.1g echoes it.
224500discard500 + 19 = 519 > 24: discarded. The unpatched server sent back 500 bytes from a 24-byte record: 479 of them server memory past the record's end. The video's hook: the 495 bytes after “bread” were her own 16 bytes of padding, then 479 bytes of other people's data.
38364echo64 + 19 = 83 ≤ 83: it fits, so 1.0.1g echoes it.
42465,535discard65,535 + 19 = 65,554 > 24: discarded. The unpatched server sent back 65,535 bytes from a 24-byte record: 65,514 of them server memory past the record's end.
55116echo16 + 19 = 35 ≤ 51: it fits, so 1.0.1g echoes it. The record has more than 16 bytes of padding, which RFC 6520 allows: the check only asks that the claim fits.
62016,384discard16,384 + 19 = 16,403 > 20: discarded. The unpatched server sent back 16,384 bytes from a 20-byte record: 16,367 of them server memory past the record's end.
73718echo18 + 19 = 37 ≤ 37: it fits, so 1.0.1g echoes it.
83921discard21 + 19 = 40 > 39: discarded. Only one byte over, so the unpatched reply took a byte of the sender's own padding and nothing else; the check doesn't guess intent, any claim that doesn't fit is thrown away.

Lines 2, 4, 6 and 8 are discarded. Together the lies took 82,360 bytes of staging's memory. Normal logs showed none of this; only a debug trace did.

3. New key and certificate

RowServerNew key?Why
1shop.bytebakery.exampleyesit ran 1.0.1f with a 2013 key: patch, then a new key and certificate, then reset customer sessions and ask for new passwords.
2mail.bytebakery.exampleno0.9.8 never had the bug: nothing leaked, nothing to replace.
3supplier.bytebakery.exampleyespatched on 8 Apr, but its key sat for two years in the memory of a vulnerable 1.0.1e. Patching doesn't take back a key that may already have leaked.
4stock.bytebakery.exampleyesoffice network only, but anyone on it (a guest's laptop, a compromised PC) could send a heartbeat. Vulnerable since 2012: new key and certificate too.
5ovens.bytebakery.exampleno1.0.0 never had the bug: nothing to replace.
6staging.bytebakery.exampleyesthe trace shows lying heartbeats reached it: assume its key and the test accounts leaked. New key and certificate, and never share keys between staging and the shop.
7pay.bytebakery.examplenoits key was born after the fix, on a version that never leaked it.

The order that matters: patch first, then the new key and certificate (a new key on an unpatched server can leak again), then revoke the old certificate and reset sessions and passwords.
